# P02 时间点与时长查询：回答策略规格 v0.1

> 文档状态：v0.1 已实施到程序（阈值和基线口径仍为 provisional）  
> 适用项目：AI Coach Lab v0.1  
> 目标原型：P02「时间点与时长查询」  
> 本轮范围：回答内容编排与生成策略，不修改路由、安全政策和其他原型

---

## 1. 文档目的

本规格用于回答一个核心问题：

> 当用户询问“昨晚几点睡、几点醒、睡了多久、深睡多久、REM 多久、清醒多久、多久睡着”时，系统应如何在准确回答的基础上，补充恰当的信息，并由 LLM 生成自然、不死板的 ToC 表达？

本规格不试图为每一种自然语言问法手写固定答案，而是定义：

1. P02 的能力边界；
2. 不同指标族的默认信息包；
3. 哪些额外事实可以成为候选洞察；
4. 什么变化值得展示；
5. 产品、程序和 LLM 各自负责什么；
6. 数据不足、表达歧义和越界关系如何处理；
7. 后续实现与评测应满足什么标准。

---

## 2. 已确认的产品原则

以下原则来自当前讨论，视为本版已经确认的方向。

### 2.1 最终自然语言由 LLM 生成

Python 不拼接以下固定话术：

```text
你昨晚大约23:31睡着。
```

程序只负责提供结构化事实、候选关系和回答约束；整段自然语言由 LLM 生成。

### 2.2 不把全部原始数据直接交给 LLM 自由发挥

程序先整理本次回答允许使用的内容：

```text
必答事实
＋默认相邻事实
＋安全的候选洞察
＋表达限制
```

LLM 只能在这个范围内组织回答，不得自行创造个人事实、事件、因果和医学结论。

### 2.3 不按用户的每一种措辞维护答案

以下问法都映射到同一个标准字段：

```text
我昨晚几点睡的？
昨儿什么时候睡着？
昨天晚上几点入睡的？
```

Router 最终输出：

```json
{
  "prototype": "P02",
  "metric": "bedtime_start"
}
```

后续回答策略只处理 `bedtime_start`，不再分别维护四套问法。

注意：`我是不是很晚才睡？` 不是纯粹的时间点同义问法。它除了查询入睡时间，还要求进行“早/晚”的个人比较或状态判断，应由 Router 识别其中的判断诉求；初版可先作为 Bad Case 记录和迭代，不把它硬塞进 P02 的时间点查询同义词。

### 2.4 回答应完成“最小完整理解”，但不展开成整夜报告

系统不应只返回一个孤立字段，也不应因为用户关心昨晚就罗列所有睡眠数据。

推荐原则：

```text
用户明确询问的结果
＋完成当前理解所必需的相邻信息
＋最多一条值得补充的个人变化
```

### 2.5 简单问题允许只有简单答案

如果没有显著变化、历史不足或没有可靠关系，回答默认信息包即可，不强行制造洞察。

### 2.6 P02 不负责医学判断和复杂因果分析

P02 可以陈述：

- 时间点；
- 持续时长；
- 占比；
- 与个人历史的差值；
- 可以直接计算的时间构成关系；
- 多项指标同时变化的事实。

P02 不应直接判断：

- 正常或异常；
- 是否健康；
- 是否失眠；
- 晚睡是否导致睡眠效率下降；
- 单晚睡眠是否导致 HRV 或恢复分变化。

## 3. P02 的产品定位

### 3.1 一句话定位

> 围绕用户询问的睡眠时间点或持续时长，准确回答核心结果，补齐同一睡眠片段的必要信息，并在存在可靠、显著的个人变化时最多补充一条相关洞察。

### 3.2 P02 负责的问题

```text
我昨晚几点睡着的？
我今天几点醒的？
昨晚睡了多久？
昨晚在床上待了多久？
深睡有多久？
REM 有多久？
昨晚清醒了多久？
我昨晚用了多久才睡着？
```

### 3.3 相似但不属于 P02 的问题

| 用户问题 | 推荐原型/能力 | 原因 |
|---|---|---|
| 深睡是什么意思？ | P07 | 指标概念解释 |
| 我昨晚深睡正常吗？ | P08 | 单次状态解读 |
| 为什么昨晚只睡了5小时？ | P14 | 睡眠同域分析 |
| 最近一周是不是睡得更晚？ | P11 | 周期趋势比较 |
| 今晚怎么才能早点睡？ | P22/P23 | 行动或计划 |
| 我是不是失眠？ | 诊断边界/安全承接 | 涉及医学诊断 |

### 3.4 主原型不等于整段回答只能使用一个能力

最终 ToC 回答可以由多个能力模块编排，但必须明确主次。

例如：

```text
用户问“几点醒”
主能力：P02，回答醒来时间和睡眠时长
可选扩展：恢复分模块、主观感受采集模块
```

恢复分和“你今天感觉怎么样”不应写死在 P02 内部；应由上层回答编排策略根据晨间场景、数据变化和用户偏好决定是否加入。

## 4. P02 指标范围与指标族

当前 P02 注册字段：

```text
bedtime_start
bedtime_end
total_sleep_duration
time_in_bed
deep_sleep_duration
rem_sleep_duration
awake_time
latency
```

为避免逐字段、逐问法重复配置，初版归纳为四个指标族。

### 4.1 指标族 A：睡眠边界

字段：

```text
bedtime_start
bedtime_end
```

用户心智：

```text
这一晚从什么时候开始，到什么时候结束，总共睡了多久？
```

默认信息包：

```text
用户所问边界
＋另一个睡眠边界
＋总睡眠时长
```

### 4.2 指标族 B：总体时长

字段：

```text
total_sleep_duration
time_in_bed
```

用户心智：

```text
这一晚实际睡了多久，睡眠区间是什么？
```

默认信息包：

```text
用户所问时长
＋入睡时间
＋醒来时间
```

`time_in_bed` 可额外补充实际睡眠时长，帮助区分“在床时间”和“真正睡着的时间”。

### 4.3 指标族 C：睡眠阶段

字段：

```text
deep_sleep_duration
rem_sleep_duration
```

用户心智：

```text
这一睡眠阶段持续了多久，在整晚中占多少？
```

默认信息包：

```text
阶段时长
＋占总睡眠比例
```

个人基线比较作为候选扩展，不默认套用人群正常值。

### 4.4 指标族 D：连续性相关时长

字段：

```text
awake_time
latency
```

用户心智：

```text
这一晚有多少时间没有真正睡着，和平时相比如何？
```

默认信息包：

```text
用户所问时长
＋与个人近期水平的比较（历史充分时）
```

候选扩展可以包含睡眠效率或实际睡眠时长，但不得把 `awake_time` 推断成夜醒次数。

## 5. 各字段的回答内容合同

下表定义“必须给 LLM 的内容”和“可选给 LLM 的内容”，不是固定文案。

| 目标字段 | 必答事实 | 默认相邻事实 | 可选候选方向 | 禁止推断 |
|---|---|---|---|---|
| `bedtime_start` | 入睡时间 | 醒来时间、总睡眠 | 比平时早/晚；时间变化如何对应总睡眠变化 | 晚睡导致效率、HRV或恢复下降 |
| `bedtime_end` | 醒来时间 | 总睡眠、入睡时间 | 比平时早/晚；早醒是否对应总睡眠减少 | 早醒的病因 |
| `total_sleep_duration` | 总睡眠时长 | 入睡—醒来区间 | 与个人基线比较；变化主要来自晚睡或早醒；与连续性共同变化 | 是否达标、是否失眠、一定改善恢复 |
| `time_in_bed` | 卧床时长 | 实际睡眠时长、两者差值 | 在床时间与实际睡眠的差异 | 把全部差值等同清醒或失眠 |
| `deep_sleep_duration` | 深睡时长 | 占总睡眠比例 | 与个人近期深睡水平比较 | 人群统一正常值、单晚医学结论 |
| `rem_sleep_duration` | REM时长 | 占总睡眠比例 | 与个人近期REM水平比较 | 单晚REM高低对应某种疾病或心理状态 |
| `awake_time` | 清醒总时长 | 与个人基线比较 | 与效率、总睡眠共同变化 | 夜醒次数、夜醒发生时间、夜醒病因 |
| `latency` | 入睡潜伏期 | 与个人基线比较 | 与入睡时间、效率共同变化 | 入睡困难诊断、原因推断 |

## 6. 回答的内容层级

一次 P02 回答由三个内容层级组成。

### 6.1 第一层：Required Facts

用户明确询问的内容，必须出现在回答第一处。

示例输入：

```json
{
  "metric": "bedtime_start",
  "display_value": "23:31"
}
```

要求：回答开头首先解决“几点睡”。

### 6.2 第二层：Default Companions

根据指标族自动补齐的最小完整信息。

示例：

```json
{
  "bedtime_end": "07:12",
  "total_sleep_duration": "6小时56分钟"
}
```

这一层由默认信息包决定，不属于洞察。

### 6.3 第三层：Candidate Insight

只有在以下条件同时满足时才允许加入：

1. 数据完整；
2. 历史样本足够；
3. 变化达到展示门槛；
4. 与用户所问内容直接相关；
5. 关系类型被产品允许；
6. 对用户提供了默认信息包以外的新信息。

每次回答最多选择一条候选洞察。

---

## 7. 默认信息包与候选洞察的区别

### 7.1 默认信息包

作用：补齐用户理解当前睡眠片段所需的事实。

特点：

- 不要求存在显著变化；
- 不负责解释；
- 由指标族确定；
- 有数据就默认提供；
- 不称为洞察。

示例：

```text
入睡时间＋醒来时间＋总睡眠
```

### 7.2 候选洞察

作用：从个人变化和指标关系中找出本次最值得补充的一件事。

特点：

- 必须有比较或关系证据；
- 必须通过显著性过滤；
- 不是所有回答都需要；
- 每次最多一条；
- 不允许越过证据强度表达因果。

示例：

```text
入睡晚37分钟＋醒来时间不变＋总睡眠少32分钟
→ 减少的睡眠主要出现在更晚入睡这一段
```

---

## 8. 显著性判断框架

“明显”用于判断一条变化是否值得占用用户注意力，不代表医学异常。

### 8.1 判断输入

每个候选指标至少计算：

```text
当前值
个人历史中心值
绝对变化
相对变化
个人常见波动范围
有效历史样本数
当前数据完整性
```

### 8.2 推荐判断顺序

```text
数据是否可用
→ 历史样本是否足够
→ 是否达到产品最低展示门槛
→ 是否超出个人常见波动范围
→ 是否与当前问题直接相关
```

### 8.3 MVP临时策略

在个人波动范围尚未实现前，允许使用可配置的产品展示门槛。

初始占位建议如下，需通过真实数据分布和用户研究确认：

| 指标 | 初始“值得展示”门槛 | 说明 |
|---|---:|---|
| 入睡/醒来时间 | 30分钟 | 不是医学阈值，仅过滤小波动 |
| 总睡眠/卧床时长 | 30分钟 | 不是“睡够/没睡够”判断 |
| 深睡/REM时长 | 20分钟 | 需同时考虑占比和设备波动 |
| 清醒时长 | 15分钟 | 不转换为夜醒次数 |
| 入睡潜伏期 | 15分钟 | 不用于诊断入睡困难 |
| 睡眠效率 | 3—5个百分点 | 只作为辅助候选，不在P02中判断正常异常 |

### 8.4 目标策略

历史充分时采用：

```text
超过产品最低门槛
并且
超出个人常见波动范围
```

建议使用稳健统计口径，例如中位数和 MAD/IQR，避免少量极端夜晚明显拉动均值。具体统计方法需在实现阶段由产品和数据共同确认。

## 9. 指标关系类型与表达权限

产品不需要穷举所有数值组合，但必须定义关系类型和每类关系允许说到什么程度。

### 9.1 R1：直接事实关系

例子：

```text
深睡时长占总睡眠的比例
卧床时长与实际睡眠时长的差值
```

允许：直接陈述计算结果。

### 9.2 R2：时间构成关系

例子：

```text
入睡变晚＋醒来时间基本不变＋总睡眠变短
```

允许：

```text
减少的睡眠主要出现在更晚入睡这一段。
```

不允许扩展成：

```text
晚睡导致睡眠质量下降。
```

### 9.3 R3：同域共同变化

例子：

```text
清醒时长增加＋睡眠效率降低
```

允许：描述两个变化同时出现，或以谨慎语言描述数据结构关系。

禁止：把单晚共同变化写成确定病因。

### 9.4 R4：跨域相关关系

例子：

```text
睡眠时间变化＋HRV变化
睡眠变化＋恢复分变化
```

P02单晚默认不使用。后续如需使用，应满足多晚样本、时间对齐、关系规则和对应原型的要求。

### 9.5 R5：医学解释关系

例子：

```text
晚睡导致失眠
REM偏低说明心理问题
```

P02禁止使用。

## 10. 候选洞察生成与选择

### 10.1 程序生成候选事实

示例：

```json
[
  {
    "id": "bedtime_later",
    "metric": "bedtime_start",
    "delta_minutes": 37,
    "direction": "later",
    "data_confidence": "high",
    "salience": "noticeable"
  },
  {
    "id": "wake_time_stable",
    "metric": "bedtime_end",
    "delta_minutes": 6,
    "direction": "stable",
    "data_confidence": "high",
    "salience": "supporting"
  },
  {
    "id": "duration_shorter",
    "metric": "total_sleep_duration",
    "delta_minutes": -32,
    "direction": "shorter",
    "data_confidence": "high",
    "salience": "noticeable"
  }
]
```

### 10.2 程序根据关系规则组合候选

```json
{
  "id": "later_bedtime_shorter_sleep",
  "relation_type": "time_composition",
  "relevance_to_query": "high",
  "evidence_strength": "high",
  "facts": [
    "入睡晚37分钟",
    "醒来时间基本不变",
    "总睡眠少32分钟"
  ],
  "allowed_claim": "减少的睡眠主要出现在更晚入睡这一段",
  "forbidden_claims": [
    "晚睡导致睡眠效率下降",
    "晚睡导致HRV下降",
    "晚睡导致恢复变差"
  ]
}
```

### 10.3 候选过滤

以下候选不进入 LLM：

- 数据缺失；
- 基线样本不足；
- 变化低于展示门槛；
- 与用户问题关联过远；
- 需要医学判断；
- 只是在重复默认信息包；
- 不能明确限定允许表达。

### 10.4 候选排序

推荐优先级：

```text
问题相关性
→证据强度
→变化显著性
→信息增益
→数据可信度
→安全风险
```

程序最多向 LLM 提供 2—3 条已经通过安全过滤的候选。LLM 最多选择一条，也可以选择不使用任何候选。

## 11. 产品、程序与 LLM 的职责边界

### 11.1 产品负责

- P02覆盖哪些指标；
- 指标如何分组；
- 每个指标族的默认信息包；
- 哪些指标关系允许进入候选；
- 什么变化值得展示；
- 每类关系允许表达到什么程度；
- 默认最多补充几条；
- 品牌语气和禁止话术；
- 评测标准。

### 11.2 程序负责

- 取回当前数据和历史数据；
- 单位、时间和占比计算；
- 跨午夜时间差；
- 个人基线和波动范围计算；
- 显著性过滤；
- 根据关系规则生成候选；
- 形成结构化Answer Plan；
- 记录每一步Trace；
- 生成后事实与边界校验。

程序不负责拼接最终自然语言。

### 11.3 LLM负责

- 理解用户原始表达的语气和重点；
- 首先自然回答用户明确问题；
- 将默认信息包组织成连贯表达；
- 从候选洞察中最多选择一条最相关内容；
- 保持自然、简洁、非报告腔；
- 遵守允许表达和禁止表达。

### 11.4 LLM不得负责

- 自行计算个人数值；
- 自行判断是否显著；
- 从原始全量数据自由寻找关系；
- 发明候选列表之外的因果；
- 决定医学正常异常；
- 编造夜醒次数、发生时刻或时区。

LLM生成回答前接收的结构建议如下：

```json
{

  "query_focus": {
    "metric": "bedtime_start",
    "relative_time_phrase": "昨晚"
  },
  "required_facts": {
    "bedtime_start": {
      "display_value": "23:31",
      "measurement_qualifier": "device_estimate"
    }
  },
  "default_companions": {
    "bedtime_end": "07:12",
    "total_sleep_duration": "6小时56分钟"
  },
  "candidate_insights": [
    {
      "priority": 1,
      "evidence_strength": "high",
      "facts": [
        "入睡时间比个人近期水平晚37分钟",
        "醒来时间与个人近期水平相差6分钟",
        "总睡眠比个人近期水平少32分钟"
      ],
      "allowed_claim": "减少的睡眠主要出现在更晚入睡这一段",
      "forbidden_claims": [
        "晚睡导致睡眠效率下降",
        "晚睡导致HRV下降"
      ]
    }
  ],
  "answer_policy": {
    "answer_query_first": true,
    "max_optional_insights": 1,
    "allow_no_insight": true,
    "address_user_as": "你",
    "tone": "natural_consumer_health",
    "avoid_preambles": [
      "根据你的数据",
      "从记录来看",
      "关于你的问题"
    ],
    "hide_unless_asked": [
      "具体年月日",
      "原始数据未提供时区",
      "source_session_id",
      "内部字段名"
    ]
  }
}
```

完整的原始检索结果仍保留在 Debug Trace 中，但不作为可以自由复述的用户回答内容。

## 13. 表达风格规范

### 13.1 推荐风格

- 使用“你”，避免过度客套；
- 直接从答案开始；
- 使用用户原来的时间指代，例如“昨晚”“今天早上”；
- 时间点使用“大约”或自然表达体现设备估计属性；
- 一次只讲一个重点；
- 句子短、可快速扫读；
- 数据比较要说明比较对象；
- 可以温和，但不夸张鼓励或制造焦虑。

### 13.2 禁止或默认隐藏

正常查询中不主动出现：

```text
根据您的数据
根据系统提供的数据
您在2026年5月6日的入睡时间是……
原始数据未提供时区
source_session_id
当前Demo仅使用目标日期对应的主睡眠记录
```

### 13.3 允许说明具体日期或时区的条件

仅在以下情况说明：

- 用户直接询问具体日期；
- “昨晚”“前天”等指代存在歧义；
- 跨时区旅行可能改变睡眠夜归属；
- 多条睡眠记录需要用户确认；
- 时区缺失确实影响结果解释。

## 14. 各指标族的参考输出

以下仅用于表达目标展示，不是固定模板。

### 14.1 问入睡时间：只有默认信息包

> 你昨晚大约23:31睡着，今天7:12醒来，一共睡了6小时56分钟。

### 14.2 问入睡时间：存在高价值候选洞察

> 你昨晚大约23:31睡着，今天7:12醒来，一共睡了6小时56分钟。入睡比平时晚了37分钟，但起床时间基本没变，所以这晚少掉的睡眠主要在前半段。

### 14.3 问醒来时间

> 你今天大约7:12醒来，昨晚23:31左右睡着，一共睡了6小时56分钟。

### 14.4 问总睡眠时长

> 你昨晚一共睡了7小时9分钟，睡眠记录大约从23:31持续到今天7:12。

### 14.5 问卧床时长

> 你昨晚在床上大约7小时41分钟，其中实际睡眠约7小时9分钟。

### 14.6 问深睡时长

> 昨晚设备记录到1小时28分钟深睡，大约占整晚睡眠的五分之一。

### 14.7 问REM时长

> 昨晚设备记录到1小时42分钟REM睡眠，约占总睡眠的23%。

### 14.8 问清醒时长

> 昨晚的睡眠记录中共有54分钟处于清醒状态，比你最近几晚多了23分钟。

### 14.9 问入睡潜伏期

> 昨晚设备估计你用了大约18分钟入睡，和最近几晚相比快了约10分钟。

## 15. 数据不足与降级策略

### 15.1 当前值存在，但相邻字段缺失

只回答当前值，不补造默认信息包。

```text
你昨晚大约23:31睡着。醒来时间和总睡眠记录目前不完整，所以这次先不展开整晚区间。
```

是否需要主动说明缺失原因，由后续数据状态规则决定。

### 15.2 当前值存在，但个人基线不足

默认信息包正常回答，不生成个人变化洞察。

### 15.3 当前值缺失

不让 LLM从其他字段反推。

回答应说明当前不能确认，并提供最短恢复路径，例如同步或检查记录。

### 15.4 时间指代不清

用户说“那天”“那次”但上下文无法解析时，先澄清日期，不猜测。

### 15.5 多段睡眠

初版仍沿用主睡眠口径。若存在多段记录且用户问题可能指向午睡或第二段睡眠，应澄清或明确采用的记录，不静默合并。

### 15.6 数据质量不足

有记录不等于记录可靠。P02只能使用已经通过数据质量门槛的字段；质量门槛和覆盖率能力后续应与P06共用。

## 16. 对话编排与跨能力扩展

### 16.1 恢复分

恢复分不属于P02默认信息包。可在以下条件下作为上层编排模块加入：

- 当前为晨间首次交互；
- 恢复分数据可用；
- 产品确认用户需要晨间概览；
- 不会掩盖用户明确询问的时间点；
- 对恢复分的表达经过P10或对应能力规则。

### 16.2 “你今天感觉怎么样”

不应每次机械追加。建议触发条件：

- 当日尚未收集主观感受；
- 当前数据存在值得验证的变化；
- 用户过去愿意参与这类互动；
- 当前场景适合晨间Check-in；
- 系统能够保存并在后续分析中使用该反馈。

### 16.3 用户偏好

V1不做自动个性化。后续可学习：

```text
回答详细度偏好
是否喜欢个人比较
是否愿意回答主观感受
是否经常打开详情
```

用户偏好只能影响可选扩展，不能改变核心事实、安全边界和数据准确性。

## 17. 生成后校验要求

LLM生成后至少检查：

1. 是否首先回答了目标字段；
2. 所有时间和数值是否来自 Answer Plan；
3. 是否使用了错误日期；
4. 是否主动输出了时区缺失等内部元数据；
5. 是否使用“根据您的数据”等禁止开场；
6. 是否使用超过一条额外洞察；
7. 是否把共同变化改写成因果；
8. 是否输出医学正常异常或诊断；
9. 是否编造夜醒次数、时间或事件；
10. 是否出现Answer Plan中不存在的个人数据。

校验失败时允许携带具体错误原因重新生成一次；连续失败则降级为只使用必答事实和默认信息包重新生成。

## 18. P02专项评测框架

### 18.1 路由评测

验证不同自然语言是否稳定识别为正确字段：

```text
几点睡 → bedtime_start
几点醒 → bedtime_end
睡了多久 → total_sleep_duration
在床多久 → time_in_bed
深睡多久 → deep_sleep_duration
REM多久 → rem_sleep_duration
清醒多久 → awake_time
多久睡着 → latency
```

### 18.2 Retrieval评测

验证：

- 核心字段正确；
- 默认相邻字段齐全；
- 单位和换算正确；
- 睡眠阶段占比正确；
- 个人基线样本数正确；
- 跨午夜时间计算正确。

### 18.3 Insight评测

验证：

- 未达到门槛时不生成候选；
- 达到门槛时生成正确事实；
- 关系组合符合配置；
- 不允许的因果不进入候选；
- 候选顺序符合相关性和证据强度；
- 无可靠候选时允许空列表。

### 18.4 Response评测

建议满分项：

| 维度 | 核心要求 |
|---|---|
| 直接性 | 第一处解决用户明确问题 |
| 准确性 | 数值、日期归属、单位正确 |
| 完整性 | 合理整合默认信息包 |
| 相关性 | 最多一条与问题直接相关的补充 |
| 自然度 | 不使用报告腔和无信息量开场 |
| Grounding | 不出现Answer Plan之外的个人事实 |
| 边界 | 不诊断、不武断因果、不编造事件 |
| 克制 | 没有可靠洞察时不强行分析 |

### 18.5 初版Case矩阵

建议至少覆盖：

- 四个指标族各2—3条标准表达；
- 口语改写；
- 显著变早/变晚；
- 总睡眠变长/变短；
- 时长稳定但连续性变化；
- 基线不足；
- 默认相邻字段缺失；
- 当前值缺失；
- 跨午夜；
- 多段睡眠；
- 试图诱导因果；
- 试图询问医学正常异常。

## 20. 建设分期

### V1：默认信息包与自然表达

- 四个指标族；
- 默认信息包；
- Answer Plan；
- LLM生成完整回答；
- 去除具体年月日、时区缺失和报告腔；
- 基础生成后校验。

V1不主动做复杂洞察。

### V2：个人显著变化和候选关系

- 个人历史中心值；
- 展示门槛；
- 候选事实；
- P02范围内的关系规则；
- 最多一条可解释洞察；
- Trace展示候选与选择过程。

### V3：ToC个性化与跨模块编排

- 回答详细度偏好；
- 晨间Check-in；
- 恢复分等跨能力组合；
- 用户主观感受闭环；
- A/B测试不同回答策略；
- 用真实行为数据优化默认编排。

## 21. 当前待产品确认事项

以下内容仍需讨论，不应直接视为最终结论。

### D01：默认信息包长度

当前建议：睡眠边界默认返回“入睡＋醒来＋总睡眠”。

待确认：在语音、通知、首页卡片等场景是否需要更短版本。

### D02：默认是否使用个人比较

当前建议：个人比较不属于所有指标族的默认信息包；只有达到显著性门槛时进入候选洞察。连续性指标可例外讨论。

### D03：显著性初始门槛

当前文档中的30分钟、15分钟和3—5个百分点均为占位建议，需要结合数据分布、竞品体验和用户研究确认。

### D04：历史基线窗口

当前系统使用近7次主睡眠平均。待确认是否改为近14晚、28晚，是否排除旅行、生病、缺失严重等特殊夜晚。

### D05：深睡/REM默认是否展示占比

当前建议展示阶段时长＋占总睡眠比例。待确认普通用户是否容易理解，以及是否需要先完成指标科普。

### D06：回答长度

当前建议：默认信息包1句；有候选洞察时最多增加1句。待通过ToC测试验证。

### D07：测量限定语

当前建议对时间点和睡眠阶段使用“大约”“设备估计/记录”等自然限定，但不每次重复完整设备限制。

### D08：恢复分和主观感受

当前建议不放入P02默认信息包，留给上层晨间编排。待确认产品是否已有固定晨间Check-in形态。

### D09：LLM选择权

当前建议：程序提供排序后的2—3个安全候选，LLM最多选1条，也允许不选。待通过评测确认模型选择是否稳定；如不稳定再收紧为程序指定选中候选。

## 23. 核心结论

P02不应维护“每个用户问法对应一段固定答案”，也不应将全量睡眠数据直接交给LLM自由分析。

推荐结构是：

```text
用户问法
→ Router识别P02和标准字段
→ 指标画像确定默认信息包
→ 数据层准备核心、相邻字段和历史数据
→ 洞察层生成并过滤候选关系
→ Answer Planner形成回答Brief
→ LLM生成完整自然语言
→ Validator检查事实和边界
```

产品需要设计的是指标族、默认信息包、关系类型、显著性和表达权限；不需要穷举全部数值组合和最终话术。
